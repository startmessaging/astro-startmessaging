## Overview

Webhooks push events to your server as they happen, so you do not have to poll. Each delivery is an HTTPS `POST` with a JSON body, signed with your endpoint's secret.

You can add endpoints in two ways:

- **Dashboard:** **Developers → Webhooks → Add endpoint.** Enter a public `https://` URL, an optional description and the events to receive. The signing secret is shown on the endpoint's details, where you can also send a test event, see the delivery log, redeliver, rotate the secret and turn the endpoint off or on.
- **API:** `GET /api/v1/webhooks`, `POST /api/v1/webhooks` and `DELETE /api/v1/webhooks/{id}`, with the `webhooks:manage` scope. This is the subscribe/unsubscribe pair Zapier, Make and Pabbly-style tools use.

Endpoints per workspace depend on your plan:

| Plan | Webhook endpoints |
|---|---|
| Free trial | 5 |
| Developer (every size, Free included) | 2 |
| Team | 1 |
| Business | 5 |
| Enterprise | Unlimited |

Disabled endpoints count too. Adding one beyond the limit answers `403 PLAN_LIMIT_REACHED` with `details.limit: "max_api_webhooks"`.

## Events

| Event | When | Read scope |
|---|---|---|
| `message.received` | A customer messaged your workspace. | `messages:read` |
| `message.sent` | Meta accepted an outbound message (dashboard, API, automation or campaign). | `messages:read` |
| `message.delivered` | Delivery receipt: the message reached the phone. | `messages:read` |
| `message.read` | Read receipt. | `messages:read` |
| `message.failed` | Meta reported the message could not be delivered. | `messages:read` |
| `contact.created` | A contact was created (inbound message, dashboard or API; not per row of a CSV import). | `contacts:read` |
| `contact.opted_out` | Consent withdrawn (STOP, dashboard, API). Not fired when a customer turns off marketing inside WhatsApp. | `contacts:read` |
| `contact.opted_in` | Consent given back (START, dashboard, API). | `contacts:read` |
| `conversation.assigned` | A conversation's assignment changed. | `conversations:read` |
| `conversation.resolved` | A conversation's resolution changed. | `conversations:read` |
| `template.status_updated` | A template's review status changed. | `templates:read` |
| `campaign.completed` | A campaign finished sending. | `campaigns:read` |

There is also a `ping` event, sent only by **Send test event** in the dashboard (see below).

## Subscribe through the API

`POST /api/v1/webhooks` with `url`, `events` (at least one) and an optional `description` (up to 200 characters). Besides `webhooks:manage`, the key must hold the **read scope of every event family** it subscribes to (table above). A missing one is `403 INSUFFICIENT_SCOPE`, and `details.missing` lists every scope to add.

```bash
curl -X POST "{{WA_API_BASE}}/api/v1/webhooks" \
  -H "Authorization: Bearer sm_live_your_api_key" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com/webhooks/startmessaging",
    "description": "Order system",
    "events": ["message.received", "message.delivered", "message.failed"]
  }'
```

```javascript
const res = await fetch("{{WA_API_BASE}}/api/v1/webhooks", {
  method: "POST",
  headers: {
    Authorization: "Bearer sm_live_your_api_key",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    url: "https://example.com/webhooks/startmessaging",
    description: "Order system",
    events: ["message.received", "message.delivered", "message.failed"],
  }),
});
const { data } = await res.json();
// Store data.secret now: it is how you verify deliveries.
console.log(data.webhook.id, data.secret);
```

```python
import requests

res = requests.post(
    "{{WA_API_BASE}}/api/v1/webhooks",
    headers={"Authorization": "Bearer sm_live_your_api_key"},
    json={
        "url": "https://example.com/webhooks/startmessaging",
        "description": "Order system",
        "events": ["message.received", "message.delivered", "message.failed"],
    },
)
data = res.json()["data"]
print(data["webhook"]["id"], data["secret"])  # store the secret now
```

- `GET /api/v1/webhooks` lists every endpoint in the workspace (made in the dashboard or the API), newest first. It is paginated like every list (`limit`, default 25, and `cursor`; see [Pagination & Idempotency](/docs/whatsapp/pagination-and-idempotency)). Secrets are never listed.
- `DELETE /api/v1/webhooks/{id}` deletes an endpoint (`204`). It works even after your subscription has lapsed.
- `POST /api/v1/webhooks` accepts an `Idempotency-Key` header.

### Endpoints created with an API key

An endpoint created through the API lives inside its key's grant. It receives an event only while that key is not revoked and still holds the event family's read scope, checked again before every attempt, including retries and redeliveries.

- **Revoking the key** disables the endpoints it created (`disabledReason: "key_revoked"`).
- **Narrowing the key's scopes** drops the event families it can no longer read from those endpoints. An endpoint left with none is disabled (`disabledReason: "key_scope_reduced"`).
- Neither can be switched back on beyond the key's current grant.
- Endpoints a member creates in the dashboard belong to no key and are bound by none.

## URL rules

- HTTPS only, on port **443**, resolving only to **public** internet addresses.
- No username or password in the URL; verify deliveries with the signing secret instead.
- Up to **2,048 characters** once encoded (each non-ASCII character or space takes several).

Saving an endpoint checks what it can without DNS and refuses a bad URL with `422 WEBHOOK_URL_NOT_ALLOWED`. `details.reason` is one of:

| Reason | Fix |
|---|---|
| `invalid_url` | Enter a full URL starting with `https://`. |
| `unsupported_scheme` / `https_required` | Use an `https://` address. |
| `credentials_not_allowed` | Remove the username and password. |
| `port_not_allowed` | Use the standard HTTPS port, 443. |
| `private_address` | `localhost` or an IP on a private or local network. Use a public address. |
| `url_too_long` | Keep it to 2,048 characters or fewer once encoded; anything over 2,048 is refused. |

A hostname is resolved on every connection, not when saved. One that resolves to a private, loopback or link-local address is accepted, but every delivery to it fails with `blocked_address` in the delivery log. Click **Send test event** right after saving to catch this.

## The envelope

Every delivery has the same body:

```json
{
  "id": "evt_5b2e8f9a-1c3d-4e5f-8a9b-0c1d2e3f4a5b",
  "type": "message.received",
  "createdAt": "2026-10-02T10:15:00.000Z",
  "workspaceId": "d1e2f3a4-b5c6-4d7e-8f9a-0b1c2d3e4f5a",
  "data": { }
}
```

`id` is the event id, the same across retries and redeliveries: use it to deduplicate. `data` depends on `type`, as below.

### Customers without a phone number

Someone with a WhatsApp username can write to you without Meta sharing their number. Until they share it, the payloads name them by Meta's business-scoped user id instead (a two-letter country code, a period, an optional `ENT.`, then up to 128 letters and digits, such as `IN.13491208655302741918`; the pattern is `^[A-Z]{2}\.(?:ENT\.)?[A-Za-z0-9]{1,128}$`):

| Event | Number (may be `null`) | User id |
|---|---|---|
| `message.received` | `message.from`, `contact.phone` | `message.fromUserId`, `contact.waUserId` |
| `message.sent` and the receipts | `message.to` | `message.toUserId` (see below) |
| `contact.*` | `contact.phone` | `contact.waUserId` |
| `conversation.*` | `conversation.contactPhone` | `conversation.contactWaUserId` |

Key your records on our ids (`contactId`, `conversationId`) rather than the phone number, and treat every number field as nullable.

## Payloads

### message.received

```json
{
  "id": "evt_5b2e8f9a-1c3d-4e5f-8a9b-0c1d2e3f4a5b",
  "type": "message.received",
  "createdAt": "2026-10-02T10:15:00.000Z",
  "workspaceId": "d1e2f3a4-b5c6-4d7e-8f9a-0b1c2d3e4f5a",
  "data": {
    "message": {
      "id": "c4e1b2a3-9d8f-4e7a-b6c5-0a1b2c3d4e5f",
      "conversationId": "3f6c2a1e-8b4d-4c7a-9e21-5d0b7f9a1c33",
      "contactId": "9a8b7c6d-5e4f-4a3b-8c2d-1e0f9a8b7c6d",
      "from": "+919812345678",
      "fromUserId": "IN.13491208655302741918",
      "type": "interactive",
      "text": "Yes, confirm order",
      "media": null,
      "reply": { "kind": "button", "id": "cod_confirm", "title": "Yes, confirm order" },
      "context": { "messageId": "7d1e2f3a-4b5c-4d6e-8f9a-0b1c2d3e4f5a", "clientReference": "order-1042" },
      "form": null,
      "referral": null,
      "timestamp": "2026-10-02T10:15:00.000Z"
    },
    "contact": { "id": "9a8b7c6d-5e4f-4a3b-8c2d-1e0f9a8b7c6d", "phone": "+919812345678", "waUserId": "IN.13491208655302741918", "name": "Asha Verma" }
  }
}
```

| Field | Description |
|---|---|
| `from` | The sender's number in E.164, or `null` for a username-only customer. |
| `fromUserId` | Meta's business-scoped user id for the sender, when Meta sent one; otherwise `null`. |
| `type` | `text`, `template`, `image`, `video`, `audio`, `document`, `sticker` or `interactive`. `interactive` is a tap on your reply buttons or list (see `reply.kind`) or a submitted WhatsApp Form (`form` is set). Kinds the API does not model (location, contact card, reaction, a tap on a template's quick-reply button) are `text`: a placeholder such as `[location]`, or the button's label for a quick reply. Branch on `reply`, not on the text. |
| `text` | The message's words. An uncaptioned photo has `text: null`; a caption is also in `media.caption`. For a submitted form it is a one-line summary (at most 300 characters), such as `Full name: Asha Rao · City: Pune`. Read the answers from `form`. |
| `media` | `type`, `mimeType`, `filename`, `caption`, or `null`. Metadata only: no download URL. |
| `reply` | What the customer tapped, or `null`. `kind` is `button` (interactive reply button), `list` (list row) or `quick_reply` (a template quick-reply button). For a reply button or list row you sent, `id` is the id you gave the option: branch on it, since `title` is the label as the customer saw it and can change with translation. For a template quick-reply button sent through the API, you cannot set the `id`: match `title` (the button text as approved) and find your message with `context.clientReference`. |
| `context` | Set when the customer replied to a specific message (tapping a button on it counts). `messageId` is our id for that message, or `null` when it is not one of this workspace's; `clientReference` is the reference it was sent with. A forwarded message is not a reply. |
| `referral` | Set on the first message from a Click-to-WhatsApp ad or boosted post: `sourceType`, `sourceId`, `sourceUrl`, `headline`, `body`, `ctwaClid` (any of them `null` when Meta left it out). `ctwaClid` is the click id Meta's Conversions API takes. |
| `form` | Set when the customer submitted a WhatsApp Form or WhatsApp's address request. See below. |
| `contact` | `id`, `phone` (may be `null`), `waUserId` and `name`, or `null` when there is no contact. |

A submitted WhatsApp Form:

```json
"form": {
  "kind": "flow",
  "flowToken": "lead-77",
  "flowId": "1234567890123456",
  "flowName": "Lead capture",
  "fields": [
    { "key": "screen_0_Full_name_0", "label": "Full name", "value": "Asha Rao" },
    { "key": "screen_0_City_1", "label": "City", "value": "Pune" },
    { "key": "screen_0_Opt_in_2", "label": "Opt in", "value": true }
  ],
  "raw": null
}
```

- `kind` is `flow` for a WhatsApp Form and `address_message` for an address request. Treat any other value as a form too.
- `flowToken` is the token the form was sent with. Set it per send with `template.buttonParameters: [{ "index": 0, "subType": "flow", "text": "lead-77" }]` and match the answers to your record with it. It is `unused` when the send gave none.
- `flowId` and `flowName` say which Flow it was, when that is certain; `null` otherwise.
- `fields` lists every answer in WhatsApp's order. Map on `key` (WhatsApp's response key; nested answers are flattened with dots, such as `values.city`). `label` is a readable label made from the key. `value` is a string, boolean, number, array or `null`.
- `raw` is WhatsApp's answer as received, only when it could not be read as JSON (then `fields` is empty).

## Headers

| Header | Value |
|---|---|
| `Content-Type` | `application/json` |
| `X-SM-Event` | The event type, such as `message.received`. |
| `X-SM-Event-Id` | `evt_...`, identical across retries and redeliveries, and equal to the body's `id`. |
| `X-SM-Delivery` | The id of this delivery's attempt series (as shown in the delivery log). |
| `X-SM-Timestamp` | Unix seconds, fresh on every attempt. |
| `X-SM-Signature` | `v1=` followed by the hex HMAC-SHA256. During a secret rotation, several comma-separated `v1=` values. |

## Verify signatures

Verify every delivery before trusting it:

1. Take the **raw** request body exactly as received. Parsing and re-serialising JSON changes the bytes.
2. Compute HMAC-SHA256 of `X-SM-Timestamp`, a dot, and the raw body: `"<timestamp>.<raw body>"`.
3. The key is the **whole signing secret, including the `whsec_` prefix**, as text. Do not strip the prefix or base64-decode the rest. Libraries written for the Standard Webhooks `whsec_` format do exactly that, and will reject every delivery.
4. Compare the hex digest, in constant time, with each `v1=` value in `X-SM-Signature`. Accept the delivery if **any** one matches.
5. Refuse a timestamp more than **5 minutes** from your clock: that is what a replay looks like.

`X-SM-Signature` carries one `v1=` value per signing secret: the current secret first, then each secret a rotation retired within the last 24 hours (at most four values). When you **Rotate secret** in the dashboard, the old secret keeps signing for 24 hours alongside the new one, so you can update your server without missing events.

### Node.js

```javascript
import { createHmac, timingSafeEqual } from "node:crypto";

// rawBody: the request body exactly as received (a Buffer or string),
// before any JSON parsing. secret: the whole "whsec_..." string.
export function verifySignature(rawBody, headers, secret) {
  const timestamp = String(headers["x-sm-timestamp"] ?? "");
  // Refuse a missing timestamp, and anything older than 5 minutes.
  if (!/^\d+$/.test(timestamp)) return false;
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false;

  const expected = Buffer.from(
    createHmac("sha256", secret)
      .update(`${timestamp}.`)
      .update(rawBody)
      .digest("hex"),
  );

  // While a secret is being rotated, several signatures arrive; accept any.
  return String(headers["x-sm-signature"] ?? "")
    .split(",")
    .some((part) => {
      const signature = Buffer.from(part.trim().replace(/^v1=/, ""));
      // Compare byte lengths first: timingSafeEqual throws on a mismatch.
      return (
        signature.length === expected.length &&
        timingSafeEqual(signature, expected)
      );
    });
}
```

With Express, read the raw body for this route only:

```javascript
import express from "express";

const app = express();
const seen = new Set(); // use your database or Redis in production

app.post(
  "/webhooks/startmessaging",
  express.raw({ type: "application/json" }),
  (req, res) => {
    if (!verifySignature(req.body, req.headers, process.env.SM_WEBHOOK_SECRET)) {
      return res.sendStatus(401);
    }
    const event = JSON.parse(req.body.toString("utf8"));
    res.sendStatus(200); // answer within 5 seconds, then do the work
    if (seen.has(event.id)) return; // at-least-once: deduplicate on the body's id
    seen.add(event.id);
    queueForProcessing(event);
  },
);
```

### Python

```python
import hashlib
import hmac
import time


# raw_body: the request body bytes exactly as received.
# headers: case-insensitive, as Flask and Django provide them.
# secret: the whole "whsec_..." string.
def verify_signature(raw_body: bytes, headers, secret: str) -> bool:
    timestamp = headers.get("X-SM-Timestamp", "")
    # ASCII digits only: str.isdigit() also accepts characters like "²".
    if not (timestamp.isascii() and timestamp.isdigit()):
        return False
    # Refuse anything older than 5 minutes.
    if abs(time.time() - int(timestamp)) > 300:
        return False

    expected = hmac.new(
        secret.encode(), f"{timestamp}.".encode() + raw_body, hashlib.sha256
    ).hexdigest()

    # While a secret is being rotated, several signatures arrive; accept any.
    for part in headers.get("X-SM-Signature", "").split(","):
        signature = part.strip().removeprefix("v1=")
        # compare_digest raises TypeError on a non-ASCII str.
        if signature.isascii() and hmac.compare_digest(signature, expected):
            return True
    return False
```

With Flask:

```python
from flask import Flask, request

app = Flask(__name__)

@app.post("/webhooks/startmessaging")
def startmessaging_webhook():
    if not verify_signature(request.get_data(), request.headers, WEBHOOK_SECRET):
        return "", 401
    event = request.get_json()
    enqueue(event)  # deduplicate on event["id"] in your worker
    return "", 200
```

Every check fails closed: a missing or non-numeric timestamp, a missing signature or a malformed `v1=` value returns `false` (answer `401`), never an exception.

## Delivery and retries

- **At least once.** Retries and manual redeliveries repeat an event. Deduplicate on the body's `id` after the signature checks out. It equals `X-SM-Event-Id`, but only the body is signed, so a replayed request could change the header and not the `id`.
- **Unordered.** Events can arrive out of order; use the timestamps in `data`.
- **Answer with a 2xx fast**, then do the work afterwards (queue it). Each request allows 5 seconds to connect, 5 seconds for your response headers and 5 seconds between parts of the body, and 10 seconds in all. Anything other than a 2xx, including any redirect or a timeout, is a failure.
- **Retries** after a failure: 1 minute, 5 minutes, 30 minutes, 2 hours, 6 hours and 12 hours. Seven attempts in about 20 hours, each signed with a fresh timestamp.
- **Auto-disable.** A delivery is exhausted when all 7 attempts failed. An endpoint is turned off after 50 exhausted deliveries in a row, or after 24 hours of failing (counted from the first exhausted delivery) with at least 3 exhausted, and flagged in the dashboard (`disabledReason: "failing"`). Fix it, turn it back on in **Developers → Webhooks**, then redeliver what failed from its delivery log. Events are not kept while an endpoint is off, and a redelivery is refused while it is off.

## FAQ

**Why does signature verification always fail?**
The usual causes: hashing parsed-and-re-serialised JSON instead of the raw body, stripping the `whsec_` prefix or base64-decoding the secret (use the whole string as text), or forgetting the dot between the timestamp and the body.

**Do I need to answer a verification challenge?**
No. There is no `hub.challenge` handshake. Save the endpoint, then use **Send test event** to check it answers a signed `ping` with a 2xx.

**Can I receive webhooks on localhost or a private IP?**
No. Endpoints must be public HTTPS on port 443. For local development, use a tunnelling service that gives you a public HTTPS URL.

**Will I get the same event twice?**
Possibly. Delivery is at least once. Store each event's `id` and skip ones you have already handled.

**How do I change the secret without downtime?**
Click **Rotate secret**. The old secret keeps signing alongside the new one for 24 hours, so deliveries carry both `v1=` values while you update your server.
